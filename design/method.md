# method — 설계를 쓰는 방식

엔진 저장소(`hkt-adventure-proto/design/method.md`)의 "흐름 파일" · "책임 파일" 절을 그대로 쓴다. 기반 이하의 명세(기반 · 줄기 · 도전 · 조합 · 경험 · 세계)는 게임의 것이라 여기에 없다.

설계는 명세 둘이다. 흐름 · 책임. 그 위에 목표와 개요(`README.md`) 하나, 그 아래 피드백 하나가 있다.
파일 하나가 하나를 말한다. 같은 정의를 두 파일에 적지 않는다. 다른 명세의 것은 이름과 링크로 가리킨다.

| 내용 | 주인 | 다른 명세가 하는 일 |
|---|---|---|
| 외부 입력의 처리 순서 | 흐름 | 필요한 흐름을 참조한다 |
| 데이터 필드와 기능 | 책임 | 그 기능의 이름으로 쓴다 |
| 엔진이 내놓은 면의 사실 | 엔진의 `web/ONLINE.md` §1 · 코드는 `src/protocol/engine.ts` | 베끼지 않고 가리킨다 |
| 서비스의 값(포트 · 데이터셋 · NPC 묶음 · 한계) | `service.config.json` | 이름으로 가리킨다 |

- 흐름에 없는 호출은 구현에 없다. 책임에 없는 데이터는 구현에 없다.
- 구현에 필요한 것이 설계에 없으면 코드보다 먼저 설계를 고친다.

## 흐름 파일

`NN-<이름>.md`. 번호가 순서다.

```text
# 흐름 N. <이름> — <한 줄>
트리거: 외부 입력 하나.
한 줄: 무엇이 일어나는가.
## 순서
누가 누구를 어떤 순서로. 들여쓰기가 순서, 줄 끝 [모듈]
### <절>
표. # · 누가 · 무엇을 · 결과. 멈추는 자리는 ◇, 다른 흐름은 ⇒, 거절은 ✕
## 멈추는 자리
값이 놓여 다음 입력을 기다리는 곳
## 이어지는 흐름
## 규칙
## 미정
```

- 단계는 `개념.기능` 으로 쓴다. 책임 파일(또는 README 의 앱)의 기능과 이름이 같다. `npm run index` 가 그것을 검사한다.
- 줄 끝의 [모듈] 은 `[앱]` · `[계정]` · `[게이트웨이]` · `[세션]` · `[플릿]` · `[스토리지]` · `[엔진]`(밖) 가운데 하나다. 프로세스가 갈리면 ` — 컨트롤 플레인` 처럼 덧붙인다.
- 의사코드는 쓰지 않는다. 코드가 그것이다.

## 책임 파일

`<모듈>.md`. 모듈마다 하나.

```text
# <모듈> — 책임
<모듈>이란, <한 문장>.
- 모르는 것 · 지키는 것. 서너 줄
생성 트리. 들여쓰기가 누가 만드는가
## 개념
### <이름>
- 데이터: 필드:타입. 불변이면 (불변). 없으면 없음
- 기능: 무엇을 하는가. 한두 줄. 기능 이름은 `이름(인자)` 로 쓴다
- 생애: 누가 만들고 언제 사라지는가
## 소켓
메시지 · 방향 · 보내는 것 · 답의 표
## 미정
```

- 다른 모듈의 개념은 `모듈.개념` 으로 가리킨다.
- 코드는 개념 하나 = 파일 하나, 이름은 책임 문서 그대로다(`src/<모듈>/<개념>.ts`).

## 피드백 파일

`00-feedback/feedback.md` 표 하나. 구현 중 새로 드러나 책임 · 흐름의 말이 늘어야 닫히는 것만 온다. 값을 고르면 되는 것은 그 자리에서 결정해 설계에 적는다.
무엇 칸은 **드러남** · **지금** · **문제** · **풀면** 넷을 완결된 문장으로 쓴다. 번호는 늘기만 한다.

## 쓰기

- 문서와 코드 주석은 한국어, 파일 이름은 영어.
- 살아 있는 문서에는 현재 상태만 적는다. 경위는 git 이 든다.
