# 흐름 14. 관측 — 수집기 · 관측 페이지의 요청

트리거: 밖의 수집기 · load balancer · 운영자의 브라우저가 보내는 http 요청. 프로세스마다 Monitor 의 내부 주소(`monitorPort`)에 `GET /health` · `GET /metrics` · `GET /observe` · `GET /observe/page`.
한 줄: 프로세스가 제 일을 할 수 있는가를 답하고, 제 수치를 글로 내고, 흐름의 단계가 지나간 흔적을 지금 흘린다. 판단과 알림은 수집기(밖)의 일이다.

## 순서

```text
GET /health       → Monitor.health                                   [앱]
GET /metrics      → Monitor.metrics                                  [앱]
GET /observe/page → Monitor.page                                     [앱]
GET /observe      → Monitor.metrics → Monitor.stream                 [앱]
                      흐름 1 ~ 13 의 단계마다 Monitor.trace → 열린 stream 마다
```

| # | 누가 | 무엇을 | 결과 |
|---|---|---|---|
| 1 | Monitor.health | 이 프로세스가 듣고 있는가. 내려가는 가운데면 503 — load balancer 가 새 요청을 다른 곳으로 보낸다. 컨트롤 플레인은 활성인지 대기인지도 답한다 | 200 또는 503 |
| 2 | Monitor.metrics | 그 role 의 수치 — API 서버: 요청 · 거절의 수. 게이트웨이: 열린 접속 · 버린 글. 컨트롤 플레인: 존마다 세션 · 대기열 · 빈 슬롯, 인스턴스마다 state · 사람 수 · 틱 지연. 노드: 인스턴스마다 state · 틱 지연 · 마지막 저장 뒤의 시간 | 글 |
| 3 | Monitor.page | 관측 페이지 한 장 — 흐름의 지도(map) 위에 흐름 · 단계마다의 흔적과 단위마다의 상태를 그린다. 지도에서 아직 src 에 서지 않은 단계는 흐리게 | 페이지 |
| 4 | Monitor.metrics | stream 의 첫 글 — 2 의 수치 하나와 recent 의 흔적 전부 | |
| 5 | Monitor.stream | 읽는 이를 readers 에 넣는다. 그 뒤로 흔적이 날 때마다 그 흔적을, Clock 의 간격마다(흐름 5) 2 의 수치를 흘린다. 읽는 이가 닫으면 뺀다 | 읽는 이 ◇ |

### 흔적

흐름 1 ~ 13 의 단계 하나가 끝날 때마다 그 개념이 Monitor.trace 로 흔적 하나를 남긴다. 흔적은 그 프로세스 안에서 앱이 준 함수로 가고, recent 와 열린 stream 마다에 들어간다.

| 칸 | 뜻 |
|---|---|
| at | 끝난 때(ms) |
| flow · step | 흐름의 번호와 그 표의 `#`. 흔적의 이름이다 |
| run | 한 번의 실행을 묶는 이름 — 입장 하나 · 접속 하나 · Clock 의 한 번 · 명령 하나. ⇒ 로 이어진 흐름은 같은 run 을 잇는다 |
| unit | 그 단계가 다룬 단위의 이름 — 인스턴스 · 존 · 노드 · 게이트웨이. 없으면 `-` |
| end | `ok` · `wait`(◇ 다음 입력을 기다린다) · `refused`(✕) · `failed`(「실패하면」으로 갔다) |
| state | 단위의 state 가 바뀌었으면 바뀐 뒤의 값. 아니면 없다 |

## 실패하면

- 상태를 바꾸지 않으므로 그만둘 것이 없다. 답하고 끝나거나(1 ~ 3), 읽는 이가 닫을 때까지 흘린다(5).
- 읽는 이가 느려 그 몫이 쌓이면 그 읽는 이의 몫만 버리고 버린 수를 다음 글에 싣는다. 단계는 기다리지 않는다.
- 프로세스가 내려가면(흐름 7) stream 은 닫힌다. 페이지는 다시 붙기를 되풀이하고, 붙으면 4 부터 다시 받는다.

## 멈추는 자리

- 열린 stream 이 읽는 이마다 하나. recent 에 최근의 흔적(상한 `traceKeep`).

## 이어지는 흐름

- 없음. 흔적은 흐름 1 ~ 13 이 남기고, 이 흐름은 그것을 읽기만 한다.

## 규칙

- 답과 흔적에 계정 · 캐릭터의 이름과 토큰이 없다. 수 · state · 단위의 이름뿐이다.
- 수치와 흔적은 그 프로세스가 이미 든 것이다. 관측을 위해 다른 프로세스에 묻지 않는다. 여러 프로세스를 합쳐 보는 것은 밖의 일이다 — 관측 페이지는 `?from=<주소>,…` 로 여러 Monitor 의 stream 을 함께 읽는다.
- 흔적은 단계 하나에 하나다. Link 의 글마다 남기지 않는다.
- 흔적을 남기는 것은 단계의 결과를 바꾸지 않는다. trace 는 기다리지 않고 실패하지 않는다.
- 흐름의 지도(map)는 design/01-flows 에서 뽑는다. 손으로 쓰지 않는다 — 흐름의 `#` 을 바꾸면 그 흔적을 남기는 코드도 같은 커밋에서 바꾼다.
- Monitor 의 http 는 내부 주소에만 연다. 밖에 열린 포트(Api · 게이트웨이)에는 없다.
- load balancer 가 빼는 것은 새 접속을 받을 자리뿐이다. 이미 열린 접속은 건드리지 않는다.
